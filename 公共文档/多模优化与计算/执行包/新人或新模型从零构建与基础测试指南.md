### 1.1 五笔本地提交逐项说明

#### 1.1.1 Daft `6e79abf`：有界 prepared streaming runtime

完整提交为 `6e79abf5d9bd4758cc0b0917192e0c8cea60fe1e`，提交统计是 18 个文件、新增 2,463 行、删除 56 行。其中约 1,979 行是本地执行运行时代码，另有约 484 行单元测试；不能把 2,463 行全部理解为 PostgreSQL 集成代码。

这笔提交解决的是“外部生产者逐批喂入数据，而 Daft 以有限内存异步执行”的基础问题，尚不包含 PostgreSQL ABI：

- 新增 `prepared_execution.rs`，把一次执行显式建模为 prepare、push、finish、next、wait、cancel/close 生命周期；公开 `OK`、`AGAIN`、`END` 和错误结果，使上层可以非阻塞地推进执行。
- 新增 bounded streaming source。输入队列满时返回 `AGAIN`，并保留输入批次的所有权，调用方可以等待容量事件后重试，不会因背压丢批或重复消费。
- 增加执行状态、等待事件、取消并等待 worker 退出、最后错误和运行指标接口。结束输入与取消是不同状态，取消路径会唤醒被输入或输出背压阻塞的任务。
- 为 aggregate、grouped aggregate、sort、top-N、hash join 等 blocking operator 接入统一资源约束；sort 支持形成 spill run 和有界归并，top-N 对保留集执行内存门控。
- 调整 pipeline、resource manager、input sender 和相关 sink/source，使 worker 数量、in-flight batch 数量以及阻塞算子的内存使用都有明确上限。
- 新增 streaming source 和 streaming scan 测试，覆盖背压、所有权返还、finish、cancel、等待唤醒、序列化和基础计划构造。

主要审阅入口是 `src/daft-local-execution/src/prepared_execution.rs`、`sources/streaming.rs`、`spill.rs` 及各 blocking sink。该提交的边界是通用 Daft 执行能力：它不知道 PostgreSQL `PlanState`、GUC、Custom Scan 或 C ABI，也不负责 ORCA 选优。

#### 1.1.2 Daft `55f7bc2`：PostgreSQL Bridge、ABI、Arrow 与计划 IR

完整提交为 `55f7bc293aa8f125398b32f98bd990f64d90a2ed`，提交统计是 40 个文件、新增 9,713 行。该数字同时包含约 5,098 行 Bridge 正式源码、大量 ABI/IR/执行测试和 fixtures、Cargo 元数据，以及 460 行 Apache Arrow C ABI 第三方头文件；并非 9,713 行都是新写的生产逻辑。

这笔提交新增独立 workspace crate `daft-pg-bridge`，职责是把稳定、可审计的 C 边界转换成上一笔提交的 prepared execution：

- `daft_pg_bridge.h` 定义 ABI v1、状态码、配置、指标和 Arrow C Data 入出参；导出 ABI/capability 查询、open、push、finish、next、wait、metrics、cancel、close 和错误字符串生命周期函数。
- `abi.rs` 与 `error.rs` 对 Rust panic 做边界隔离，把内部错误转换成稳定、脱敏、可释放的错误对象，避免 unwinding 穿过 C ABI。
- `arrow.rs` 负责 Arrow C Data Interface 的导入、导出和释放语义。测试明确覆盖成功、`AGAIN`、错误及 close 路径上的所有权，防止 double free、泄漏和悬空引用。
- `ir.rs`、`plan.rs` 与 `expr.rs` 严格解析和校验 PgDaftPlan v1，直接 lower 到 Daft local physical plan，不在 Bridge 内再次运行一个会改变 PG/ORCA 决策的优化器。
- Bridge 冻结支持的算子集合为 Source、Project、Limit、Filter、HashJoin、HashAggregate、Sort 和 TopN，并处理 join/null、聚合、排序、溢出等语义。
- `capabilities.rs` 提供生成的能力注册表和 digest，open 前核对 ABI、运行时位和 capability digest，防止新旧 core/Bridge 静默错配。
- `execution.rs` 把内存、worker、in-flight、spill 和等待超时配置映射到 prepared runtime，同时维护边界计数、spill 清理和取消/关闭状态。
- 测试覆盖 ABI 错误生命周期、panic containment、IR 正反例、Arrow ownership、join/aggregate/sort/top-N、线程退出、内存与 spill、故障注入和 fuzz 输入。

第三方代码只包括按许可证纳入的 Arrow C ABI 头文件及许可证/说明；Bridge 的 Rust ABI、IR、执行适配、能力校验和测试均为本次项目开发。该提交不包含 PG extension 或 ORCA 代码，必须与匹配 digest 的 `pg_orca` 提交配对使用。

#### 1.1.3 pg_orca `9fecc8b`：ORCA 全局选优与 PostgreSQL 执行集成

完整提交为 `9fecc8b71575f7d0aa4523fb8a6b38966c176818`，提交统计是 86 个文件、新增 22,194 行、删除 48 行。这是主体功能提交，但其中还包含 capability/IR 规范、生成结果、生成工具和 C++ selftest；“提交总行数”不等于全部都是手写 executor 代码。PostgreSQL 19 core 在本提交中保持 0 修改，集成全部位于 `pg_orca` extension 内。

该提交从优化器到执行器打通一条完整但默认关闭的链路：

- 在 ORCA memo 中引入 `PG_ROW` 与 `DAFT_ARROW` 执行格式属性、格式 enforcer、Daft 物理算子及 Project、Limit、Filter、HashJoin、HashAggregate、Sort、TopN 转换规则。Daft 方案和合法 PG 方案共同参与 memo，而不是在 executor 中临时替换计划。
- 增加 Daft 成本模型、边界转换成本、资源估算和 fragment fusion。最终 winner 仍由 ORCA 全局成本比较产生，可形成“PG 算子在 Custom Scan 上方、PG 子计划在其下方”的混合计划。
- 在一次 planner 调用开始时冻结不可变 capability snapshot；`off` 不产生候选，`auto` 在 Bridge 缺失或不兼容时保留 PG 计划，`force` 用稳定原因码暴露拒绝原因。规划中途不会重新探测并改变候选集合。
- 定义无裸指针的 PgDaftPlan v1 canonical IR、稳定 operator/field ID、序列化、checksum 和 capability digest；final validator 在创建可执行计划前检查算子、类型、表达式、资源边界和跨边界契约，失败时 fail closed。
- DXL-to-Plan 翻译器只把 ORCA 已选中的 Daft fragment 生成为 `Custom Scan (DaftExec)`，PG-owned child plan 保留在 `custom_plans` 中，由 PostgreSQL 正常初始化和遍历。
- `compat/executor/daft_exec.cpp` 在 backend 主线程拉取 PG child tuple，批量转换为 Arrow 后以 push/poll/wait 状态机驱动 Bridge；处理 rescan、cancel、ResourceOwner、错误清理、EXPLAIN 指标和子计划结束。
- `daft_arrow.cpp` 实现 PG Datum/tuple 与 Arrow C batch 的类型及所有权转换；`daft_bridge_loader.cpp` 使用 `dlopen`/`dlsym` 一次性校验完整 vtable、ABI、能力和路径信任条件，`pg_orca.so` 不产生对 Rust Bridge 的直接动态依赖。
- CMake 同时支持 `PG_ORCA_ENABLE_DAFT=ON/OFF`。关闭构建保留必要的 canonical 类型和 stub，不要求 Rust/Daft；开启构建也仍以 `pg_orca.daft_enable=off` 为运行默认值。
- 当前冻结提交已经包含两个收尾修复：no-Daft 构建所需公共头文件的可见性，以及 push 返回 `DPG_END` 时先释放 PG-owned pending batch、再轮询 Bridge 以暴露详细 pipeline 错误或正常 EOF。
- capability YAML/schema、golden、生成脚本和 selftest 与实现同提交冻结，用于检查注册表漂移、IR 编解码、validator、memo 格式属性和成本决策。

主要审阅目录是 `gpopt/daft/`、`compat/executor/`、`include/pg_orca/daft/`、ORCA physical/xform/cost/property 修改、`libgpopt/src/translate/` 和 `pg_orca.cpp`。该提交完成的是功能集成，不等于完成生产门禁：P2 的 72 小时 soak、发布批准和远端 push 均不在其范围内。

#### 1.1.4 pg_orca `13132b1`：16 项 Daft 集成回归

完整提交为 `13132b108bdd245622aa47c94553b9a15ca3aef6`，提交统计是 34 个文件、新增 3,856 行、删除 7 行，恰好由 16 个 SQL、16 个 expected、回归 schedule 和 test harness 修改组成；本提交没有生产实现代码。

16 项用例不是只检查 SQL 结果，而是分层冻结下列行为：

- 边界与加载：`daft_arrow` 检查类型/Arrow 边界，`daft_loader` 检查 off/auto/force、ABI 和 capability 拒绝，`daft_basic` 检查最小端到端路径。
- 优化与计划：`daft_memo`、`daft_rules`、`daft_filter`、`daft_join`、`daft_aggregate`、`daft_sort_topn` 检查候选、winner、成本、算子语义和 EXPLAIN 形状。
- 混合计划：既覆盖 PostgreSQL Aggregate 位于 `Custom Scan (DaftExec)` 上方，也覆盖 Aggregate 在上、Daft Custom Scan 居中、PG Join child 在下的三层计划，防止把 Daft 误实现成只能接管整棵计划树。
- 生命周期：`daft_planstate` 检查 `custom_ps`、walker、child end 和 guard 恢复；`daft_plancache` 检查缓存计划/失效；`daft_cancel` 检查取消和 worker 收敛。
- 失败与降级：`daft_fallback`、`daft_errors` 和 `daft_parallel` 检查 fail-closed、错误清理、auto 保留 PG 方案以及 postmaster/parallel 等进程门禁。
- 可观测性：`daft_explain` 检查计划字段、边界指标、spill/资源计数及执行前后 reconcile，避免“结果正确但实际路径不明”。

expected 文件同时冻结关键 `Custom Scan` 字段和混合计划树，不应在不了解计划变化原因时用新输出整批覆盖。当前执行包记录的是 Daft 16/16 通过，合并后的 pg_orca 全 schedule 34/34 通过；这些结果是基础验收，不替代第 10 节的正式 P2 gate。

完整提交为 `5277154ae13cfabdeb2f487e385f82e3f50eac71`，提交统计是 3 个文件、新增 126 行、删除 1 行。它不再修改优化或执行语义，而是把已经验证的功能变成默认安全、可回滚的可选交付物：

### 1.2 推荐的离线交付方式

当前三个仓库都是 shallow repository；普通 Git bundle 不携带 `.git/shallow` 边界，恢复后可能无法遍历 `origin/main..HEAD`，因此这里不使用 bundle。交付人应归档每个仓库的完整 `.git` 元数据和 Git 已跟踪源码，同时排除 Daft `target/` 等巨大构建产物。下列命令只读取仓库，不会 push：

```bash
cd /home/qiumc/data/code/cpp
export PGD_WORKSPACE="$PWD"
export PGD_HANDOFF_DIR=/path/to/new-empty-handoff-directory

mkdir -p "$PGD_HANDOFF_DIR"

for repo_name in postgres19 pg_orca daft; do
  (
    cd "$PGD_WORKSPACE/$repo_name"
    {
      printf '.git\0'
      git ls-files -z
    } | tar --create --gzip \
      --file="$PGD_HANDOFF_DIR/$repo_name.tar.gz" \
      --null --files-from=-
  )
done

tar -C "$PGD_WORKSPACE" -czf "$PGD_HANDOFF_DIR/integration-docs.tar.gz" \
  integration/pg19-pgorca-daft \
  公共文档/多模优化与计算

(
  cd "$PGD_HANDOFF_DIR"
  sha256sum postgres19.tar.gz pg_orca.tar.gz daft.tar.gz \
    integration-docs.tar.gz > SHA256SUMS
)
```

`integration/pg19-pgorca-daft` 和 `公共文档/多模优化与计算` 不在上述三个源码仓库中，必须单独传递；不要只交三份仓库归档。归档前仍应检查日志不含密码、token、credential、业务行数据或未脱敏地址。

接收方先校验哈希，再恢复目录：

```bash
export PGD_HANDOFF_DIR=/path/to/received-handoff-directory
export PGD_WORKSPACE=/path/to/new/workspace

cd "$PGD_HANDOFF_DIR"
sha256sum -c SHA256SUMS

mkdir -p "$PGD_WORKSPACE"

for repo_name in postgres19 pg_orca daft; do
  mkdir "$PGD_WORKSPACE/$repo_name"
  tar -C "$PGD_WORKSPACE/$repo_name" -xzf \
    "$PGD_HANDOFF_DIR/$repo_name.tar.gz"
done

tar -C "$PGD_WORKSPACE" -xzf "$PGD_HANDOFF_DIR/integration-docs.tar.gz"
```

恢复完成后再执行第 3 节的精确 SHA 和 ahead 数量检查。离线归档不是远端发布，也不得由接收方擅自 push。

## 2. 目录和变量约定

下文假设三个仓库处于同一工作区：

```text
<workspace>/postgres19
<workspace>/pg_orca
<workspace>/daft
<workspace>/integration/pg19-pgorca-daft
```

在终端中设置隔离路径。`PGD_BUILD_ROOT` 和 `PGD_INSTALL_ROOT` 会被干净构建脚本删除并重建，因此只能指向专用子目录，不能指向源码、工作区根目录或已有数据库目录。

```bash
cd /home/qiumc/data/code/cpp

export PGD_WORKSPACE="$PWD"
export PGD_BUILD_ROOT="$PGD_WORKSPACE/.build/pg19-pgorca-daft/newcomer"
export PGD_INSTALL_ROOT="$PGD_WORKSPACE/.install/pg19-pgorca-daft/newcomer"
export PGD_RUNTIME_ROOT="$PGD_WORKSPACE/.runtime/pg19-pgorca-daft/newcomer"
export PGD_JOBS=8
```

机器内存较小时可把 `PGD_JOBS` 降为 `2` 或 `4`。不要复用其他人的 `.build`、`.install` 或 `.runtime` 目录作为“从零构建”证据。

## 3. 源码和执行包预检

先核对 SHA、提交数量和工作树：


## 4. 从零构建 Daft-enabled 完整栈

项目提供的唯一推荐干净构建入口是：

```bash
bash integration/pg19-pgorca-daft/build_clean.sh
```

该脚本会执行：

1. 只删除并重建上面显式设置的 `PGD_BUILD_ROOT` 与 `PGD_INSTALL_ROOT`；
2. 以 `--enable-debug --enable-cassert` 构建并安装 PostgreSQL 19；
3. 使用下列冻结命令构建 Release Rust Bridge：

   ```bash
   cargo build --locked --release -p daft-pg-bridge --no-default-features
   ```

4. 把 `libdaft_pg_bridge.so` 安装到 PostgreSQL 私有的 `lib/postgresql/pg_orca/`；
5. 使用 Ninja、Debug 和 `PG_ORCA_ENABLE_DAFT=ON` 构建、安装 pg_orca。

不要把 Rust Debug Bridge 当作基础验收产物；它体积和性能画像不同。构建完成后检查关键产物：

```bash
test -x "$PGD_INSTALL_ROOT/bin/postgres"
test -x "$PGD_INSTALL_ROOT/bin/pg_config"
test -f "$PGD_INSTALL_ROOT/lib/postgresql/pg_orca.so"
test -f "$PGD_INSTALL_ROOT/lib/postgresql/pg_orca/libdaft_pg_bridge.so"
test -f "$PGD_INSTALL_ROOT/share/postgresql/extension/pg_orca.control"

"$PGD_INSTALL_ROOT/bin/pg_config" --version
file "$PGD_INSTALL_ROOT/lib/postgresql/pg_orca.so"
file "$PGD_INSTALL_ROOT/lib/postgresql/pg_orca/libdaft_pg_bridge.so"
nm -D "$PGD_INSTALL_ROOT/lib/postgresql/pg_orca/libdaft_pg_bridge.so" | \
  rg 'dpg_open_v1'
```

`pg_orca.so` 通过 `dlopen` 延迟加载 Bridge，因此 `ldd pg_orca.so` 不应显示对 `libdaft_pg_bridge.so` 的直接动态依赖。

## 5. 独立验证 no-Daft 构建

no-Daft 构建只验证 pg_orca 的关闭路径，不能覆盖刚安装的 Daft-enabled 产物。选择一个此前不存在的专用目录：

```bash
export PGD_OFF_BUILD="$PGD_WORKSPACE/.build/pg19-pgorca-daft/newcomer-off"
test ! -e "$PGD_OFF_BUILD"

cmake -S "$PGD_WORKSPACE/pg_orca" \
  -B "$PGD_OFF_BUILD" \
  -G Ninja \
  -DPG_CONFIG="$PGD_INSTALL_ROOT/bin/pg_config" \
  -DCMAKE_BUILD_TYPE=Debug \
  -DPG_ORCA_ENABLE_DAFT=OFF

cmake --build "$PGD_OFF_BUILD" --target pg_orca -j"$PGD_JOBS"
```

核对关闭构建图：

```bash
rg '^PG_ORCA_ENABLE_DAFT:BOOL=OFF$' "$PGD_OFF_BUILD/CMakeCache.txt"
rg -m1 -- '-DPG_ORCA_ENABLE_DAFT=0' "$PGD_OFF_BUILD/build.ninja"

if rg -q 'daft_bridge_loader.cpp.o' "$PGD_OFF_BUILD/build.ninja"; then
  echo 'ERROR: OFF build graph contains Daft loader' >&2
  exit 1
fi

if ninja -C "$PGD_OFF_BUILD" -t commands pg_orca | tail -n 1 | \
   rg -q 'daft_bridge_loader.cpp.o|libdaft_pg_bridge'; then
  echo 'ERROR: OFF link contains Daft loader or Rust Bridge' >&2
  exit 1
fi

if ldd "$PGD_OFF_BUILD/pg_orca.so" | rg -qi 'daft|arrow'; then
  echo 'ERROR: OFF module has Daft/Arrow dynamic dependency' >&2
  exit 1
fi

if nm -D "$PGD_OFF_BUILD/pg_orca.so" | rg -q 'dpg_[a-z0-9_]*'; then
  echo 'ERROR: OFF module exposes or requires dpg symbols' >&2
  exit 1
fi

echo 'no-Daft build: PASS'
```

预期 OFF 构建仍会编译 `daft_exec.cpp` 和 `daft_arrow.cpp` 中的禁用 stub，但不会编译 loader、链接 Rust Bridge 或开放 Daft 运行时。不要把 OFF 产物安装到 `PGD_INSTALL_ROOT`，否则会覆盖下一节所需的 ON 产物。

## 9. 常见问题

### 9.1 SHA 与本文不一致

最常见原因是只 clone 了远端。不要自行 cherry-pick 猜测提交，也不要 reset 到 `origin/main`；向交付人索取当前仓库或离线 bundle。

### 9.2 no-Daft 构建找不到 `arrow/c/abi.h`

先确认 pg_orca HEAD 是 `5277154`，并确认 `CMakeLists.txt` 对 canonical Bridge include path 的处理来自 `9fecc8b`。不要恢复已经清理的 C++ Arrow builder 或 Bridge stub。

### 9.3 测试报告 Bridge unavailable

确认使用的是本次 `build_clean.sh` 生成的 Release Bridge，并检查：

```bash
test -f "$PGD_INSTALL_ROOT/lib/postgresql/pg_orca/libdaft_pg_bridge.so"
sha256sum "$PGD_INSTALL_ROOT/lib/postgresql/pg_orca/libdaft_pg_bridge.so"
```

不要从其他安装目录复制未知版本的 Bridge；ABI、capability digest 与 pg_orca 必须成对。

### 9.4 `daft_sort_topn` 偶发通用 push 错误

这通常说明运行时仍加载了 DEC-072 之前的 `pg_orca.so`。重新执行 `cmake --install "$PGD_BUILD_ROOT/pg_orca"`，确认 `PG_CONFIG` 指向本次隔离安装，再重新运行测试。不要接受通用错误或放宽 expected。

### 9.5 pg_regress 报临时实例仍在运行

按错误信息使用本次 `PGD_INSTALL_ROOT/bin/pg_ctl` 停止它。只处理 `PG_ORCA_TEST_BUILD_DIR` 下明确的临时实例，不要删除其他人的数据目录。

### 9.6 端口 55419 已被占用

仅独立集群烟雾测试使用这个默认端口。可在执行 `cluster.sh` 前设置未占用端口，例如：

```bash
export PGD_PORT=55429
```

pg_regress 的 16 项临时实例不依赖该固定端口。

## 10. 本轮基础验收明确不做什么

- 不运行 `git push`、不创建远端分支、不发布包；
- 不执行正式 `run_gate.sh P2`；该命令要求至少 259200 秒，即冻结的 72 小时生产门禁；
